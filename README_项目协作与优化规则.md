# FoodPuzzle 项目协作与优化规则

> 本文件是 FoodPuzzle 项目的长期协作规则，用于约束官方 Codex、中转站 Codex CLI 以及后续接手本项目的其他智能体。
>
> 除非用户明确修改本文件中的规则，否则每次开始任务前都必须先阅读并遵守本文件。不得依赖用户在每轮对话中重复提醒。

---

## 一、规则适用范围

本规则适用于 FoodPuzzle 项目中的全部工作，包括但不限于：

- MFP 与 MPC 的瓶颈分析；
- 第一性原理分析；
- 文献检索与方法设计；
- 离线实验、开发集实验和正式实验；
- 代码修改、脚本新增和结果生成；
- 实验审查、路线冻结和失败复盘；
- `audit_records/` 中的审计记录；
- 官方 Codex 与中转站 Codex CLI 之间的任务交接。

本文件属于长期规则文件，不用于记录某一轮实验的具体结果。只有已经进入代码修改、试运行并完成结果审查的正式优化版本，才将其优化设计、证据、指标与结论集中写入 `audit_records/`；尚未进入实现与试运行的想法、讨论和候选方案只记录在 `README_工作交接.md` 中。

---

## 二、先确定任务，再执行操作

### 2.1 基本流程

每次用户提交新的提示词或工作要求后，Codex 必须先完成任务理解和执行计划，不得直接开始修改、运行或调用外部服务。

固定流程如下：

1. 阅读用户本轮提示词；
2. 阅读本规则文件；
3. 阅读与本轮任务直接相关的最新 `audit_records/`；
4. 必要时只读检查相关代码、脚本、结果和元数据；
5. 向用户说明接下来准备做什么；
6. 明确列出本轮操作范围、文件范围、实验范围、风险和停止位置；
7. 等待用户明确回复“允许”或给出等价的明确授权；
8. 获得允许后，才可以开始已批准范围内的操作；
9. 完成阶段性工作后汇报结果，并再次等待下一步批准。

### 2.2 未获得允许时的默认行为

在没有得到本轮明确授权时，默认只允许：

- 阅读用户提供的提示词；
- 阅读本规则文件；
- 阅读已有审计记录；
- 做必要的只读状态核验；
- 提出计划、风险、实验设计和权限申请。

默认不允许：

- 修改代码或配置；
- 新建实验脚本；
- 启动训练、推理或正式运行；
- 调用 DeepSeek、OpenAI 或其他外部 API；
- 读取正式测试集逐样本答案；
- 覆盖、删除、移动或重命名已有结果；
- 修改正式评测逻辑；
- 执行任何 Git 写操作；
- 将以前某一轮的“允许”自动延续到新的任务。

### 2.3 Codex 在执行前必须向用户说明的内容

在请求允许时，至少说明：

- 本轮要解决的具体问题；
- MFP 和 MPC 各自选定的唯一主要瓶颈；
- 准备采取的第一性原理分析方向；
- 准备检索或核对的原始文献范围；
- 准备修改、创建或读取的文件；
- 是否调用 API；
- 是否读取开发集或正式测试集；
- 是否可能覆盖已有结果；
- 预计生成的实验产物；
- 预先冻结的停止条件；
- 本轮是否会达到 `audit_records/` 的正式记录触发条件；若会，准备更新哪一份正式版本审查记录。

如果以上范围在执行过程中需要扩大，必须停止并重新申请允许。

## 三、MFP 与 MPC 的双任务循环优化机制

### 3.1 每轮同时推进两个任务

每一轮优化循环必须同时考虑：

- MFP；
- MPC。

但两个任务必须保持独立：

- 不联合训练；
- 不共享标签、答案或正式测试信息；
- 不使用 MFP 的结果反向帮助 MPC；
- 不使用 MPC 的结果反向帮助 MFP；
- 不把两个任务混合成一个统一优化目标；
- 分别建立假设、实验、指标、停止条件和审查结论。

### 3.2 每个任务每轮只处理一个主要瓶颈

不得在同一轮中对同一任务进行大范围、多模块、多方向同时优化。

每轮对 MFP 只选择一个当前最大的瓶颈；对 MPC 也只选择一个当前最大的瓶颈。

例如，不应在同一轮同时修改：

- 候选生成；
- Scientist Prompt；
- Reviewer Prompt；
- UniMol 使用方式；
- 检索权重；
- 评测逻辑；
- 数据切分；
- 最终执行器。

如果多个模块同时变化，实验结果将难以归因，也无法判断真正有效的改动，因此原则上禁止。

### 3.3 固定优化循环

MFP 与 MPC 各自都必须遵循以下循环：

1. **现状核验**  
   核对当前代码版本、结果版本、运行路径和已有审计结论。同时必须复查与当前瓶颈直接相关的历史成功、局部正信号和失败：只借鉴可验证的机制，不直接将旧版本认定为最优，不简单重复已被否定的实现。

2. **瓶颈识别**  
   从现有实验、逐样本错误、阶段输出和历史失败中，找出当前最大难题。

3. **第一性原理分析**  
   从任务输入、任务输出、数据生成机制、信息可得性和决策目标出发，解释瓶颈为什么存在。

4. **文献方法查询**  
   查询与该瓶颈直接相关的原始论文、官方文档或权威方法来源。不得先决定方法，再寻找与结论相符的文献包装。

5. **优化方向设计**  
   只提出一个边界明确、机制合理、可证伪的优化方向。

6. **冻结实验方案**  
   在运行前固定：
   - 输入；
   - 输出；
   - 对照组；
   - 数据切分；
   - 评价指标；
   - 超参数范围；
   - 停止条件；
   - 禁止事项。

7. **获得用户允许**  
   向用户说明完整方案，获得明确允许后再实施。

8. **执行实验**  
   只执行已批准范围，不根据中途结果临时扩大方法或反复调参挽救。

9. **结果审查**  
   同时审查主指标、具体输出能力、稳定性、机制合理性和失败类型。

10. **形成结论**  
    只能形成以下几类结论：
    - 通过并冻结；
    - 未通过并停止；
    - 获得局部信号但暂不准入；
    - 工程问题，尚不能评价方法；
    - 证据不足，需要重新定位瓶颈。

11. **按条件写入审计记录**  
    只有本轮正式优化已经进入代码修改、试运行和结果审查，才将该正式版本的优化设计与审查结论写入 `audit_records/`。纯讨论、只读分析、文献调研和未实施想法不创建审计记录。

12. **进入下一轮**  
    基于本轮证据重新识别 MFP 和 MPC 各自的新瓶颈，不得直接沿用原假设。

## 四、任务输出与评测指标必须严格区分

### 4.1 MFP

MFP 的任务输出是：

> 具体食物名称。

MFP 的官方主要评测指标是：

> 具体食物映射后的宏类别 accuracy。

因此必须严格区分：

- 任务实际输出：具体食物；
- 官方主要指标：宏类别 accuracy；
- 辅助诊断：具体食物命中、具体食物候选召回、候选类别覆盖、语义与机制合理性。

禁止：

- 在生成阶段直接输出宏类别；
- 直接把宏类别提供给 Scientist 或 Reviewer；
- 先预测宏类别，再随意找一个同类食物作为包装；
- 让优化方法只服务于类别映射器而不是具体食物恢复任务。

### 4.2 MPC

MPC 的任务输出是：

> 具体缺失分子集合。

MPC 的官方主要评测指标是：

> 官能团 F1。

同时应报告：

- 具体分子 Precision；
- 具体分子 Recall；
- 具体分子 F1；
- exact-N 是否满足；
- 食品条件支持；
- 化学与风味机制合理性。

禁止：

- 直接输出官能团而不输出具体分子；
- 为了覆盖某些官能团随意添加“官能团载体”；
- 为满足 exact-N 而无依据地填入高频分子；
- 根据正式评测器、正式测试答案或评测缓存反向设计预测。

## 五、指标提升的正确原则

### 5.1 最理想的结果

最优先接受的结果是：

- MFP 官方宏类别 accuracy 提高；
- MFP 具体食物恢复能力同时提高；
- MPC 官方官能团 F1 提高；
- MPC 具体分子恢复能力同时提高；
- 方法在食品、分子、结构和实践机制上合理。

### 5.2 无法同时提高时的判断标准

如果官方指标和具体恢复指标很难同时提升，可以将官方指标作为主要目标，但必须满足：

1. 方法仍然解决真实任务；
2. 方法没有绕过具体食物或具体分子输出；
3. 方法没有针对评测器投机；
4. 预测结果仍具有食品、分子或功能机制上的合理性；
5. 具体恢复能力不能出现无法解释的严重崩溃；
6. 指标提升必须在预先冻结的验证方案中稳定出现。

### 5.3 结果准入原则

必须区分“探索保留”与“论文主方法冻结”，不得用同一套硬门槛同时承担方向筛选和最终论文证据的职责。

**直接拒绝：**

- 主点估计非正，或方法直接要解决的阶段机制指标恶化；
- 具体食物/分子恢复显著崩溃且没有合理的功能替代机制；
- 受损样本多于受益样本，且没有预注册的安全性理由支持；
- 结果不可复现，或收益来自数据泄漏、评测漏洞、标签空间捷径。

**探索保留：**

- 官方主指标点估计为正；
- 方法所直接解决的阶段机制指标同时为正；
- 具体输出没有无法解释的安全性恶化；
- 一般要求 `wins > losses`，且无预注册的灾难性子集失败；
- 95% 置信区间和固定分块结果必须如实报告，但开发集较小时，不得将它们单独作为探索保留的硬否决。

探索保留不等于准入论文主方法，不得表述为已稳定提升。

**论文主方法冻结：**

- 仍需预先冻结的独立证据、足够统计效力的 95% 区间，或一次性正式测试；
- 不得因为某方法已被“探索保留”就放宽论文主结论的证据标准。

在上述三层判断内，继续遵守以下任务指标关系：

- **官方指标和具体恢复指标都提高**：优先冻结；
- **官方指标提高，具体恢复指标基本持平**：可以准入；
- **官方指标提高，具体恢复指标小幅下降**：只有在存在合理的功能替代或类别等价机制时才考虑；
- **官方指标提高，但具体恢复能力显著崩溃**：原则上拒绝；
- **具体恢复指标提高，但官方主指标下降**：可作为诊断结果保留，不直接进入论文主方法；
- **提升很小、置信区间跨零或折间不稳定**：不准入论文主方法；是否作为局部信号探索保留，按上述探索层条件判断；
- **收益来自数据泄漏、评测漏洞或标签空间捷径**：立即否决。

### 5.4 禁止指标导向替代任务导向

不得因为论文主要报告宏类别 accuracy 和官能团 F1，就把优化目标简化为：

- 如何最容易猜中宏类别；
- 如何最容易补齐官能团；
- 如何利用评测器行为获得更高分。

所有设计必须首先回答：

> 该方法是否在合理地恢复具体食物或具体缺失分子？

官方指标应当是任务能力自然提升后的评测结果，而不是设计的唯一服务对象。

## 六、第一性原理与文献使用规则

### 6.1 第一性原理分析要求

每轮提出优化前，必须回答：

- 当前输入中实际包含哪些信息；
- 哪些信息在当前条件下不可获得；
- 正确输出依赖什么生成机制；
- 当前模型在哪一阶段丢失了有效信息；
- 瓶颈属于候选缺失、排序错误、验证失败、执行错误，还是评测错位；
- 新方法新增了什么真实信息或归纳偏置；
- 为什么它有可能解决当前瓶颈；
- 为什么它不会只是重复使用已有信号。

### 6.2 文献查询要求

文献必须服务于已经识别的具体瓶颈。

优先使用：

- 原始论文；
- 官方论文页面；
- PMLR、ACL Anthology、NeurIPS、ICLR、JMLR、OpenReview 等权威来源；
- 官方代码仓库；
- 方法作者提供的正式文档。

不得：

- 只看二手博客就确定方法；
- 先拍脑袋决定方案，再搜索相似术语包装；
- 只因为某方法流行就强行引入；
- 引用与当前数据、输入或目标不匹配的方法。

每轮审计记录中应说明：

- 文献的核心方法；
- 与当前瓶颈的对应关系；
- 可以借鉴的部分；
- 不能直接照搬的部分；
- 本项目中的具体适配方式。

## 七、实验设计与停止条件

### 7.1 必须预先冻结

任何优化实验开始前，必须冻结：

- 研究假设；
- 基线；
- 唯一改动；
- 数据范围；
- 数据切分；
- 对照组；
- 指标；
- 置信区间或稳定性检查；
- 准入条件；
- 失败停止条件；
- 结果保存目录。

### 7.2 禁止实验后调规则

不得根据开发集或某一折结果临时：

- 更改阈值；
- 扩大候选数；
- 改权重；
- 修改 tie-break；
- 删除不利样本；
- 更改主指标；
- 改变对照组；
- 添加第二个优化模块；
- 用正式测试结果选择方法。

需要改变方案时，应停止当前实验，将其记为一次独立结果，再提出下一轮新方案并重新获得允许。

### 7.3 失败路线必须停止

当预注册停止条件未通过时：

- 明确宣布该方向未通过；
- 记录失败原因；
- 禁止围绕同一失败信号反复微调；
- 不得为了“把已经花费的工作救回来”继续扩大实验；
- 只有出现新的独立证据时，才允许重新审查该方向。


### 7.4 正式代码唯一保留原则

项目代码目录最终只保留能够支撑当前正式方法、正式运行和必要正式评测的代码。

允许在开发与调试过程中临时加入：

- `dry-run`；
- `check-only`；
- 冒烟检查；
- 临时断言；
- 临时调试输出；
- 临时验证函数；
- 临时调试脚本；
- 为定位错误而加入的短期分支或开关。

但在方法跑通并完成审查后，必须进行代码收尾：

1. 删除只服务于本轮试错和调试的临时代码；
2. 删除不再需要的 `dry-run`、`check-only`、冒烟检查入口和调试开关；
3. 删除临时验证脚本、临时补丁、一次性辅助函数和无用分支；
4. 删除临时日志输出、调试字段、测试常量和硬编码样本；
5. 合并能够合并的正式逻辑，避免为单一小功能长期保留额外代码文件；
6. 重新进行语法、静态和最小正式路径检查，确认删除调试代码后正式流程仍可运行；
7. 最终向用户汇报“临时代码已清理”以及实际保留的正式代码文件。

除非用户明确要求某个检查功能成为长期正式能力，否则不得以“以后可能有用”为由保留调试代码。

如果本轮试验失败且方案不准入，原则上应回退或删除该方案加入的实验性代码，只保留失败审查记录，不得让失败分支长期混在正式代码中。

### 7.5 最小结果与最小文件原则

除用户明确要求的文件、正式代码、正式运行必需的元数据和正式结果外，尽量不生成任何额外文件。

默认要求：

- 调试过程只在终端输出；
- `dry-run`、`check-only`、冒烟检查和中间诊断只在终端汇报；
- 不为每一步调试生成 JSON、JSONL、CSV、Markdown、日志目录或指标汇总文件；
- 不为计划、文献查询、只读分析或未实施想法创建独立报告；
- 不为一次性错误分析创建额外结果目录；
- 临时数据如确有必要，只能放在系统临时目录，并在本轮结束前删除；
- 不得把终端输出同时复制成多份内容重复的报告。

允许长期保留的产物仅包括：

1. 用户明确要求生成的文件；
2. 当前正式方法所需的代码与配置；
3. 正式运行协议必需的预测、元数据、评测摘要和可复现结果；
4. `README_项目协作与优化规则.md`；
5. `README_工作交接.md`；
6. 达到正式记录触发条件的单份 `audit_records/` 审查记录。

同一正式优化版本的设计、运行结果和审查必须尽量合并在同一份审计文件中，不再额外生成“实验方案报告”“中期报告”“错误分析报告”“指标汇总报告”等重复文档。正式结果文件本身已包含的数据，不应再复制成另一份报告。

## 八、`audit_records/` 正式优化版本审查规则

### 8.1 文件定位

`audit_records/` 不是想法笔记、每日工作日志或所有讨论的存档目录。

它只用于保存：

> 已经被用户批准为一版正式优化尝试，并且实际进入代码修改、试运行与结果审查阶段的版本级审查结果。

因此，以下内容不单独写入 `audit_records/`：

- 尚未获准实施的想法；
- 头脑风暴和候选方向；
- 纯第一性原理讨论；
- 只读仓库审计；
- 纯文献查询；
- 仅提出但没有修改代码的方法方案；
- 没有实际试运行的代码草案；
- 临时调试过程；
- 普通任务交接、权限申请和阶段性状态。

上述内容统一记录在 `README_工作交接.md` 中；只有当某个方向真正成为一版正式优化尝试后，才在对应正式审查文件中提炼必要背景。

### 8.2 创建或更新审计记录的触发条件

只有同时满足以下条件，才创建或更新一份正式优化审查记录：

1. 用户明确允许实施该优化；
2. MFP 或 MPC 的优化目标、唯一改动和实验边界已经确定；
3. 已经对正式候选代码进行实际修改；
4. 已经执行至少一次与该版本有关的试运行、正式运行或有效验证；
5. 已经取得可审查的运行结果、错误结果或工程失败证据；
6. Codex 正在对该版本进行通过、停止、回退或保留的结果审查。

以下情况尚不触发审计文件：

- 只有方案，没有改代码；
- 改了代码，但还没有运行；
- 只完成了读取和分析；
- 用户尚未允许实施；
- 只是准备 API 载荷或列出待办；
- 只是发现一个可能的研究方向。

这些状态必须进入 `README_工作交接.md`，待真正进入试运行和结果审查后，再并入该正式版本的审计记录。

### 8.3 一版正式优化对应一份审查记录

原则上，每一轮正式优化只保留一份版本级审查文件：

```text
YYYY-MM-DD_第X轮_MFP与MPC正式优化审查.md
```

如果某一轮只有一个任务真正进入正式代码修改和试运行，可以使用：

```text
YYYY-MM-DD_第X轮_MFP正式优化审查.md
YYYY-MM-DD_第X轮_MPC正式优化审查.md
```

同一版本从首次试运行到最终结论，应持续更新同一份文件，不得为以下阶段分别创建多份报告：

- 方案设计；
- 第一次调试；
- 中间结果；
- 错误分析；
- 指标汇总；
- 最终审查。

需要保留的正式内容最终统一收敛到这一份审查文件中。

### 8.4 正式审查记录的最低内容

每份正式优化审查记录至少包括：

1. 正式版本名称与日期；
2. 用户批准范围；
3. MFP 和/或 MPC 的唯一主要瓶颈；
4. 第一性原理分析摘要；
5. 与该正式改动直接相关的原始文献依据；
6. 冻结的唯一改动、基线、数据范围、指标和停止条件；
7. 实际修改的正式代码文件；
8. 临时调试代码是否已清理；
9. 实际运行方式与数据使用边界；
10. API、正式测试、结果覆盖和 Git 情况；
11. 正式或有效验证结果；
12. 与基线的配对比较和关键失败诊断；
13. 是否达到准入条件；
14. 最终结论：通过并冻结、未通过并回退、局部信号但不准入、工程失败尚不可评价；
15. 最终保留的正式代码和正式结果；
16. 已删除的临时代码与临时产物；
17. 后续不得重复的失败做法；
18. 下一轮应重新识别的问题。

审查记录应强调最终证据和版本结论，不需要逐字复制全部终端调试过程。

### 8.5 成功、失败与中断的记录边界

只要一版正式优化已经满足触发条件，即使最终失败，也应保留其单份审查记录，因为它已经形成了可复用的代码尝试和结果证据。

具体规则：

- **试运行后通过**：记录并冻结正式版本；
- **试运行后未通过**：记录失败证据，删除或回退实验性代码；
- **运行暴露工程错误，且能够审查该版本不可用**：记录工程失败和回退情况；
- **运行中断但已有有效结果可审查**：在同一文件中标明不完整，不另建中断报告；
- **尚未运行即放弃**：不创建审计文件，只在 `README_工作交接.md` 记录；
- **只有想法被否决**：不创建审计文件。

### 8.6 事实与指标类型必须区分

审查记录必须清楚区分：

- 磁盘文件直接验证的事实；
- 历史正式版本的结果；
- 当前版本新得到的结果；
- 推断；
- 尚未核实的假设；
- 本地代理指标；
- 开发集指标；
- 正式测试指标。

不得把计划写成完成，不得把终端调试输出写成正式结果，不得把本地诊断指标写成正式成绩，也不得把旧版本结果归到当前代码名下。

### 8.7 审计文件不是额外报告集合

`audit_records/` 中不应出现同一正式版本的多份重复材料。

默认不创建：

- 独立实验方案文档；
- 独立文献综述；
- 独立中期报告；
- 独立错误分析报告；
- 独立指标汇总报告；
- 独立调试日志报告；
- 只保存某个想法的审计文件。

必须保存的正式信息应合并到该版本唯一的审查记录中。运行过程和中间调试以终端输出为主，`README_工作交接.md` 只保留必要的工作状态和恢复信息。

## 九、`README_工作交接.md` 对话保存与双端同步规则

### 9.1 文件定位

项目根目录必须长期维护：

```text
README_工作交接.md
```

该文件是官方 Codex 与中转站 Codex CLI 之间共享的工作状态和对话交接文件，用于保证两套执行环境对以下内容保持一致理解：

- 用户当前要求；
- Codex 对任务的理解；
- Codex 提出的执行计划；
- 用户授予或拒绝的权限；
- 已经完成的操作；
- 当前实验进度；
- 阶段结果和错误；
- 尚未完成的事项；
- 下一步建议及其所需授权。

`README_工作交接.md` 不替代本规则文件，也不替代 `audit_records/`：

- `README_项目协作与优化规则.md`：保存长期不变的协作规则；
- `README_工作交接.md`：保存跨 Codex 环境的对话、授权、当前状态和工作时间线；
- `audit_records/`：只保存已经进入代码修改、试运行和结果审查的正式优化版本；不保存每个想法、只读分析或未实施方案。

### 9.2 每次开始任务前的强制读取顺序

官方 Codex 和中转站 Codex CLI 每次开始工作前，必须依次读取：

1. `README_项目协作与优化规则.md`；
2. `README_工作交接.md` 中的“当前状态快照”；
3. `README_工作交接.md` 最近至少三条工作时间线；
4. 最近时间线引用的 `audit_records/`、代码、脚本和结果文件；
5. 当前磁盘中的真实代码版本、结果版本和工作树状态。

不得只依据当前聊天上下文继续工作，也不得只读最后一句话就直接开始操作。

如果交接文件、审计记录与磁盘事实不一致，应先报告冲突并完成只读核验，不得自行选择对自己方便的版本继续执行。

### 9.3 项目相关对话必须持续保存

与 FoodPuzzle 项目有关的实质性对话必须按时间顺序追加到 `README_工作交接.md`。

至少必须保存：

- 用户提出的任务、修改意见和研究判断；
- 用户对指标、方法合理性和实验边界的要求；
- Codex 对任务的理解；
- Codex 在执行前提出的详细计划；
- Codex 申请的权限范围；
- 用户明确回复的“允许”“不允许”或范围调整；
- 执行过程中的重要阶段更新；
- 发现的错误、风险、版本错位和中断原因；
- 创建、修改、读取或覆盖的关键文件；
- API 调用、数据读取和 Git 操作情况；
- 实验结果、审查结论和停止原因；
- 未完成事项和恢复入口；
- 下一步建议及其需要的权限。

用户的关键要求、权限授权和纠正意见应尽量保留原意，必要时保留关键原句，不能为了简化交接而改变用户意思。

纯寒暄、重复的无实质确认和过长终端原始日志可以不逐字复制，但必须保存其有效结论，并注明完整日志所在路径。

### 9.4 固定记录格式

每次实质性工作应追加一条时间线，推荐格式：

```markdown
## YYYY-MM-DD HH:MM｜官方 Codex / 中转站 Codex CLI｜任务名称

### 用户要求

记录用户本轮要求，关键约束尽量保留原文。

### Codex 的任务理解与计划

记录执行前向用户说明的任务理解、MFP/MPC 瓶颈、方法方向、文件范围、风险、停止位置和预计产物。

### 权限申请

记录本轮申请的权限，包括是否允许：

- 修改代码；
- 新建脚本或目录；
- 调用 API；
- 使用开发集；
- 读取正式测试逐样本答案；
- 覆盖已有结果；
- 修改正式评测；
- 执行 Git 操作。

### 用户授权

记录用户的明确回复。授权范围必须按原意保存，不能扩大解释。

### 实际执行

记录真实完成的操作、命令范围、文件变化、运行状态和中断点。

### 阶段结果与审查

记录指标、错误、诊断和是否达到停止条件；只有本轮已触发正式版本审查时，才记录对应 `audit_records/` 路径。

### 当前状态

记录已经完成、尚未完成、当前有效产物和恢复入口。

### 下一步及所需权限

只记录下一项清晰工作，并明确需要用户重新批准的权限。
```

### 9.5 先写交接，再作最终汇报

每完成一个实质阶段，Codex 必须先更新 `README_工作交接.md`，再向用户发送阶段性或最终汇报。

在交接文件尚未更新时，不得声称：

- “本轮已经全部完成”；
- “上下文已经保存”；
- “官方 Codex 和中转站已经同步”；
- “下一次可以直接继续”。

如果当前环境无法写入该文件，必须明确告诉用户未能同步，并给出需要人工保存的完整交接内容，不能假装已经保存。

### 9.6 阶段性检查点

发生以下情况时，即使任务尚未结束，也必须立即向 `README_工作交接.md` 追加检查点：

- 上下文即将压缩；
- Codex 额度即将耗尽；
- API 额度不足；
- 任务需要从官方 Codex 切换到中转站 Codex CLI；
- 任务需要从中转站 Codex CLI 切回官方 Codex；
- 长任务只完成部分折、部分样本或部分脚本；
- 进程异常退出；
- 用户暂停或改变任务；
- 发现结果覆盖风险、版本断层或数据泄漏风险。

检查点必须写明：

- 当前完成到哪里；
- 哪些产物已经有效保存；
- 哪些结果尚不完整；
- 哪个命令或脚本仍在运行；
- 恢复时从哪里继续；
- 哪些步骤不得重复；
- 哪些文件不得覆盖。

### 9.7 当前状态快照与历史时间线

`README_工作交接.md` 应同时维护两部分：

1. **当前状态快照**：保存唯一一份最新状态，可随工作推进更新；
2. **历史工作时间线**：只能追加，不能删除、覆盖或把失败改写成成功。

当前状态快照至少包括：

- 更新时间；
- 最近执行环境；
- 当前代码版本；
- 当前正式结果版本；
- MFP 当前最大瓶颈；
- MPC 当前最大瓶颈；
- 已冻结方案；
- 已停止方案；
- 当前风险；
- 当前等待用户批准的事项；
- 下一步唯一建议。

更新当前状态快照时，必须在历史时间线中保留导致状态变化的对应记录。

### 9.8 授权不得跨轮自动继承

`README_工作交接.md` 中保存的历史“允许”只证明当时那一轮获得过授权，不表示后续新任务自动获得同样权限。

任何新的代码修改、API 调用、正式实验、结果覆盖、正式测试读取或 Git 写操作，都必须根据当前任务重新说明计划并获得用户明确允许。

官方 Codex 和中转站 Codex CLI 都不得以“另一个 Codex 之前获得过允许”为由扩大当前权限。

### 9.9 与 `audit_records/` 的同步关系

每轮工作都必须更新 `README_工作交接.md`。只有正式优化达到 `audit_records/` 的触发条件后，才同时完成两类记录：

- 在 `audit_records/` 中保存该正式版本的必要方法依据、正式代码改动、运行结果、审查结论和经验；
- 在 `README_工作交接.md` 中保存本轮对话、授权、操作摘要、当前状态和下一步。

如果本轮产生了正式审计文件，`README_工作交接.md` 应引用其路径，避免重复粘贴整份内容；如果本轮未达到触发条件，则不得为了形式完整而创建审计文件。

### 9.10 安全与真实性要求

交接文件中禁止保存：

- API Key；
- Token；
- Authorization Header；
- Cookie；
- 密码；
- 其他秘密凭证；
- 模型不可见的内部思维链。

交接文件必须如实记录：

- 计划与实际执行的差异；
- 失败和中断；
- 解析回退；
- 未完成样本；
- 本地代理指标与正式指标的区别；
- dev 与正式 test 的区别；
- 旧版本结果与当前代码版本的区别。

不得把计划写成完成，不得把失败隐藏，不得把旧结果归到新代码名下，也不得声称已同步实际上尚未写入的对话。

## 十、中文化要求

除第三方接口、程序固定字段、模型名称和已有代码变量外，新增内容应尽量中文化，包括：

- 文件名；
- 目录名；
- 正式审计文档；
- 正式结果中的字段说明；
- 终端指标汇报；
- 终端错误分析；
- 阶段汇报；
- 风险说明；
- 下一步计划。

已有英文技术字段可以保留，但应在中文文档中解释其含义。

不得为了中文化而破坏已有程序接口或数据格式。

## 十一、每轮结束时的固定汇报格式

每一轮阶段结束时，Codex 应至少向用户汇报：

### 1. 本轮做了什么

说明实际执行范围，不得只复述原计划。

### 2. MFP 结果

- 当前瓶颈；
- 本轮唯一改动；
- 指标与诊断；
- 是否通过；
- 是否冻结或停止。

### 3. MPC 结果

- 当前瓶颈；
- 本轮唯一改动；
- 指标与诊断；
- 是否通过；
- 是否冻结或停止。

### 4. 文件变化

列出：

- 新建文件；
- 修改文件；
- 结果目录；
- 审计记录；
- 是否覆盖历史结果。

### 5. 权限与安全说明

说明：

- 是否调用 API；
- 调用次数；
- 是否读取开发集；
- 是否读取正式测试逐样本答案；
- 是否修改正式评测；
- 是否执行 Git 操作。

### 6. 下一步

只提出一轮新的清晰动作：

- MFP 的下一个瓶颈；
- MPC 的下一个瓶颈；
- 准备进行的分析或实验；
- 需要用户批准的权限。

提出后停止，等待用户允许，不得自动进入下一轮。

---

## 十二、规则更新机制

本文件是持续维护的规则文件。

当用户提出新的长期要求时，应：

1. 先说明准备新增或修改哪一条规则；
2. 获得用户允许后更新本文件；
3. 不删除旧规则，除非用户明确要求删除或替换；
4. 在文件末尾追加更新记录；
5. 将规则变化同步写入 `README_工作交接.md`；规则更新本身不创建或修改 `audit_records/`，除非它恰好属于某个已触发的正式优化版本审查。
